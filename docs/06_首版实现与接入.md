# 06 首版实现与现有 monitor 接入

状态：事件重放与可追溯产物原型已实现。**尚未接入真实 DDR5 仿真，尚未完成 M0/M1 验收。** 本文描述当前代码实际支持的范围；02–05文档仍是完整目标架构与计划。

## 1. 本次实现的边界

已有 interface/monitor 负责观测与解码；本项目接收解码事件，生成派生的区间测量和 covergroup。没有新增 DDR5 pin interface 或指令 decoder，也没有修改旧 `causal_bayesian_attribution`。

```text
已有 monitor → adapter → 统一事件 JSONL
                        ↓
来源哈希 + requirement + min_interval规则 + run manifest
                        ↓
Python逐事件重放 + 生成SV collector + source map
                        ↓
bin → 原文/规则/代码/事件查询；来源 → 受影响bins查询
```

核心 CLI 仅依赖 Python 3.11+ 标准库，不要求安装项目或调用LLM。代码位于 [src/coverage_closure](../src/coverage_closure/)，入口是 [cc.py](../cc.py)。

| 已实现 | 尚未实现 |
|---|---|
| 严格JSON契约、来源文件哈希与引用校验、空任务拒绝 | 任意PDF自动提取、通用三层IR编译器 |
| `min_interval` 原语、latest_start、按channel/subchannel/rank隔离 | DDR5具体时序锚点、tMRD配置解析、setup/hold |
| reset/config epoch隔离、未知观测清历史、去重和冲突拒绝 | 原始CA/CS解码、多周期命令的语义事件去重 |
| at/above分类、below违例与未采样原因 | 原生coverage数据库导入、独立checker汇合 |
| 确定性SV collector与代码行/符号映射 | 商业仿真器动态对拍、UVM具体transaction适配 |
| 不覆盖旧结果的证据bundle、哈希变化检测、双向trace | 跨运行数据库、增量合并、自动修复/不可达证明 |

观察数值不能完成sign-off。所有报告固定 `closure_claim=false`；`verified_coverage=null`，`verified_hit_count=0`；不从重放结果伪造校验通过。真实monitor日志也必须等待模型验证、native coverage、checker和回归证据。

## 3. 事件适配契约

每个JSONL记录固定包含如下字段。详见 [contracts.py](../src/coverage_closure/contracts.py)；未知字段、重复JSON键和NaN均拒绝。

```json
{
  "event_id": "event.17",
  "run_id": "ddr5.actual_run_001",
  "timestamp_ticks": 4000,
  "channel": 0,
  "subchannel": 0,
  "rank": 0,
  "config_epoch": 0,
  "reset_epoch": 0,
  "kind": "command",
  "command": "VrefCA",
  "valid": true,
  "source_locator": "waves/run001.fsdb@4000ps"
}
```

上面只是格式例子，不代表存在该波形文件。当前只校验locator非空，未实现波形打开与内容验证，所以不会将其升级成verified evidence。

规则：

1. 时间单位在plan/run中一致，不做隐式转换；所有整数为非负且小于2^63，不能用bool或浮点冒充。
2. 事件来自实际monitor；run origin只能是`monitor_export`或明确的`synthetic_fixture`，拒绝driver意图。
3. 同一个channel/subchannel/rank的时间严格递增，不同scope可以同一时刻。若monitor在同一时刻产生多个有序子事件，需先设计额外顺序字段，当前v1不会猜测顺序。
4. 完全相同event_id及内容去重；同ID不同内容报错。输入已含起始和结束事件时，再重导入同一批不会增加重放计数。
5. reset事件使用`kind=reset, command=null, valid=false`，只清其标明scope；全局reset由adapter展开到所有受影响scope，或保证它们的reset_epoch增加。
6. config_epoch/reset_epoch不能回退。变化时清历史；epoch不是自动参数解析器。如果tCK/tMRD数值改变，要生成新plan和run，不能继续用旧常数。
7. `valid=false`表示这次观测不可信，保守清除scope历史。它不等于DES：一个已正确识别的DES可保持valid=true，由规则的end集合决定是否参与采样。
8. 当前规则采样使用最近start，end不消耗历史，先读旧历史再更新。DDR5只有在核对规则确实满足这些语义后才能使用此原语。

原始pin、MR状态和更丰富的checker数据暂存在外部轨迹，并通过locator关联；当前schema尚未把03文档的所有最终字段实现进去。

## 4. SV collector如何接现有monitor

```powershell
python cc.py generate --plan examples/min_interval/plan.json --out runs/generated-collector
```

得到`collector.sv`及`source_map.json`。包名带plan指纹，导入实际输出的包名。collector提供：

```systemverilog
// 在现有monitor/subscriber完成事务快照之后调用；不在driver请求时调用。
collector.observe(channel, subchannel, rank,
                  config_epoch, reset_epoch, timestamp_ticks,
                  is_reset, command_valid, command_name, outcomes);
```

调用必须串行化；由adapter处理clocking/NBA时序约定及多周期命令合并。outcomes按plan规则顺序排列：-2非目标事件，-1采样抑制，0低于下限，1等于下限，2大于下限。合法结果才调用covergroup.sample；违例使用独立计数供checker对照，不作为合法目标。

adapter还需保存event_id、locator、epoch和采样操作数。**生成collector当前没有自动导出JSONL，Python replay也不是native coverage导出器。** 接入时应从同一事务快照写事件，再通过原生数据库导出bin计数，与Python预期对比。

source_map中的`generated_symbol`是代码内名字，`native_path=null`刻意保留待绑定状态；实际实例路径必须从elaboration/coverage导出得到，禁止猜一个路径后声称已映射。

## 5. 证据bundle与查询

每次replay输出：

```text
report.json          # 每条sample、bin重放计数、阻塞项、输入与产物哈希
plan_snapshot.json   # 当前规则、要求和来源的快照
run_snapshot.json    # 来源类型、运行阶段、DUT/TB等版本标识
events.jsonl         # 输入事件原字节副本
collector.sv         # 同plan生成的collector，动态行为待验证
source_map.json      # rule→代码区段→bin符号
```

`trace-bin`返回source、requirement、rule、代码定位及关联样本；输入、来源、生成代码或核心引擎变化后返回stale（退出码3）。它是本地文件哈希一致性检查，不是签名或防恶意篡改机制；移动工作区后原输入的绝对路径需要重新建立。

`impact`按source/requirement/rule返回受影响规则和bins；当前没有测试目录和依赖运行数据库，因此不声称已经能计算最小回归测试集。
