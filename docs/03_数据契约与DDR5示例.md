# 03 数据契约与 DDR5 垂直切片

本文定义目标接口，不声称已有相应DDR5运行结果。字段中的示例 ID 是设计示意。当前已实现的较小事件契约和支持范围见[06 首版实现与接入](06_首版实现与接入.md)，不应把这里的全部字段和模块视为已实现。

## 1. 对象与最小字段

所有可变语义对象包含 `logical_id, revision, content_sha256, schema_version, created_by, created_at`。logical_id 不因改名或位置移动改变；语义变化产生新 revision。哈希采用规范化 JSON 序列化，文件本身另存字节级哈希。

| 对象 | 必填的业务字段 |
|---|---|
| SpecDocument / SpecAnchor | 文档名称/版本/文件哈希；物理页(1-based)、印刷页、章节、表/图/脚注、bbox 或文本范围、片段哈希 |
| Requirement | anchors、规范性、适用配置 predicate、解释、例外、review 状态、所属冻结 scope |
| AtomicEntity | 类型/宽度/符号/单位、值域、sampling binding 或配置来源、known-value 策略 |
| DerivedEntity | typed expression AST、dependencies、scope key、更新事件、reset、历史有效位、时钟/时间域 |
| Relation | requirement IDs、guard AST、predicate AST、参数来源、start/end 事件及锚点、测量单位 |
| CoverageObligation | relation/requirement IDs、场景维度、目标理由、合法性、checker IDs、完成证据要求 |
| BinDefinition | obligation ID、predicate AST、sample guard、配置约束、命中次数要求、语义 revision |
| GeneratedArtifact / SourceMap | 文件哈希、生成器版本、IR revision 集、生成节点→代码行/符号/bin 路径 |
| RunManifest | test/seed、完整版本指纹、argv、仿真器版本、构建/运行/导出状态、产物路径及哈希 |
| Event / SampleEvidence | run/event/sample IDs、时间与周期、配置 epoch、作用域、raw source locator、operands、guard、bin IDs |
| CheckerEvidence | checker revision、适用事件窗口、evaluated/pass/fail/not_applicable、关联诊断 |
| Diagnosis / Probe | 多个假设、support/refute/unknown 证据、区分实验、排序分数语义、确认状态 |
| Repair / ClosureDecision | base/new revision、变更、影响集、回放/回归结果、决策理由与审阅信息 |
| ExclusionEvidence | bin revision、配置 scope、约束模型/solver/假设、proof/result、有效期、失效依赖 |

关系使用明确类型：`extracted_from, formalizes, depends_on, implements, sampled_by, observed_in, supports, contradicts, supersedes, invalidates`。不要把任意字符串匹配当语义引用。一个要求可以对应多个来源；实现决策以 `design_decision` 来源记录，不能伪造规范页码。

## 2. 采样契约

统一事件包至少包含：

```text
run_id, event_id, timestamp_ticks, time_unit, cycle_index,
channel, subchannel, rank, config_epoch,
event_kind, command, command_valid, raw_CA, raw_CS_n,
reset_epoch, source_locator
```

`source_locator` 指向波形时间窗口或原始 monitor 日志记录。时间用整数 tick，指定 timeunit/timeprecision；nCK 和 ns 不隐式互换。涉及 3.5 nCK 的规则用足够细的实际时间刻度测量，单纯 posedge 周期计数不能宣称覆盖精确边界。

Derived 时序记录必须回答：按哪个 scope 保存历史、使用最近事件还是所有未决事件、何时更新、何时清除、触发当拍读 old state 还是 new state、未知值如何处理。多 rank/bank 使用规则要求的 keyed state；禁止用一个全局 prev_cmd/prev_cycle 表达所有关系。

monitor 对事件生成不可变 snapshot，再基于 snapshot 求 sample guard、operands 和 outcome；coverage 采样与证据日志使用同一 snapshot。通过 clocking block 或明确的采样调度解决 NBA 前后取值歧义，具体实现用已安装仿真器做 micro-test。run_manifest 记录所采用的采样约定。

建立 `opportunity_count → guard_true_count → sample_count → classified_count → hit_count` 计数链，并记录 guard false 的原因。只有 bin 计数为零无法区分“事件没发生”和“采样器漏采”。

## 3. 首批规则与来源

物理页与印刷页是两套编号；本文件的物理页均从 1 开始。以下为候选清单，**不是已完成审阅和实现的 DDR5 模型**。

| 批次 | 候选规则 | 来源定位 | 核对重点 |
|---|---|---|---|
| A | VrefCA / VrefCS 识别（2 项 monitor contract） | PDF 154 / 印刷 118，Table 30；Vref 专节命令表 | CA12 区分、其余固定/有效位、CS、MIR/CAI 与设备配置 |
| A | VrefCA 到后续 valid command 下限 | PDF 269–270 / 印刷 233–234，§4.24.2、Figure 117、Table 125 | `tVrefCA_Delay` 引用 tMRD；图中的起止锚点、连续多周期识别 |
| A | VrefCS 到后续 valid command 下限 | PDF 271 / 印刷 235，§4.25.2、Figure 118、Table 127 | 同样解析 tMRD；不能只替换 VrefCA 名字 |
| B | VrefCA / VrefCS CS 低电平持续时间（2 项） | Table 125/127 | 3.5–8 nCK，适用模式及注释；半周期采样能力 |
| B | VrefCA / VrefCS setup 与 hold（4 项） | 同上及相应时序图、正文 | 3 nCK；note 3 的 MR2:OP[4]=0 多周期适用条件 |

先完成 A 批再扩 B 批。MR2 配置读取、reset、NOP/DES 区分、tMRD 解析是支撑依赖，不一定都是独立论文 checkpoint。原文 Table 30 note 26 明确区分 NOP 与 DES；不能为了方便把所有 idle 周期当作 valid command。

`tMRD` 的具体数值、速度档、MR 状态和测量端点必须按当前 DUT 配置及其规范出处解析；本次不虚构固定周期数。先选一种设备/速度、单 rank/subchannel、固定 MIR/CAI，后续再加入另一合法配置验证泛化。固定配置不是删去不支持目标的借口，scope 本身要留版本。

这里的 Vref 场景属于协议命令和数字采样验证；没有模拟电压模型或硅测数据时，不宣称覆盖模拟 Vref 品质和 metastability。

## 4. 一条规则如何落实到证据

以 `req.ddr5.vrefca.next_valid_delay` 为例：

```text
SpecDocument(JESD79-5D, sha256)
  → Anchor(PDF270, print234, Table125 row tVrefCA_Delay,
           Figure117 + PDF269正文 + tMRD定义锚点)
  → Requirement(当前 scope 下的延迟要求，reviewed)
  → Atomic(VrefCA事件、valid-command事件、配置、tMRD、时钟)
  → Derived(按 rank/subchannel 保存的参考时刻、有效位、间隔)
  → Relation(guard -> measured_interval >= resolved_bound)
  → Obligation(at_bound / above_bound；负向检测另列)
  → Bin + generated source map
  → Run → Sample(start/end事件、原始时刻、阈值、guard、checker)
  → Diagnosis → directed sequence / IR或模板修复
  → New Run + regression → ClosureDecision
```

没有核对 Figure 117 的锚点之前，Relation 必须保持 draft，并阻止生成用于关闭判定的模型。多周期 CS 可能跨若干采样边沿，不可擅自把每拍相同 CA 当成互相独立的新命令。需要同时区分原始采样事件与协议语义事件。

伪 IR（仅描述字段约束，尚非可执行规则）：

```yaml
logical_id: rel.ddr5.vrefca.next_valid_delay
revision: 1
status: draft
requirement_ids: [req.ddr5.vrefca.next_valid_delay]
scope_key: [channel, subchannel, rank, config_epoch]
bound_ref: param.ddr5.tMRD
unit: time_ticks
history_valid_required: true
reset_policy: invalidate_history
start_anchor: pending_review_of_Figure117
end_anchor: pending_review_of_Figure117
sample_guard: [same_scope, history_valid, actual_valid_command]
generation_blockers: [unreviewed_event_anchors, unresolved_config_bound]
```

这两个 blockers 是防止错误确定化的必要约束；实施 M0 时解决后再冻结 revision。新增真实 run_id 之前，不预填任何 hit 或已确认根因。

## 5. 必备对拍场景

令独立审阅确定的阈值为 T、采样刻度为 q：

| 轨迹 | 预期与用途 |
|---|---|
| 已完成前置状态，间隔 T | 合法边界命中；checker 通过 |
| 间隔 T+q | 合法区间命中 |
| 间隔 T-q | 在可控负向测试中 checker 必须检测；不计合法覆盖增益 |
| 缺少起始事件直接遇到目标事件 | history_valid=false，不形成伪间隔 |
| 起始事件之后 reset | 旧历史清除，不跨 reset 合并 |
| 另一个 rank/subchannel 的事件插入 | 按声明 scope 独立计算 |
| 连续 Vref 多周期 CS | 依据已审阅锚点匹配，不因重复原始采样错误重置起点 |
| NOP 与 DES 分别插入 | 分别遵守 valid command 定义 |
| 相同命令序列更改 MR2 配置 | 以 config_epoch 隔离历史与适用条件 |
| 导出重复、日志缺失、模型 revision 改变 | 去重、拒绝不完整证据、旧数据标 stale |

部分违例可能被现有 driver 约束拦截。该部分可在独立 monitor replay/负向验证环境运行，并标明测试层级；不得把没有送到 DUT 的意图写成 DUT 检测结果。

## 6. 仿真器与 testbench 接口

以下是拟定的适配器契约，厂商命令在 M0 读取现有脚本后填写：

```python
discover_environment(config) -> EnvironmentReport
compile(snapshot, harness) -> BuildResult
run(build_id, test_plan, seed, budget) -> RunManifest
export_coverage(run_id) -> list[RawBinCount]
export_events(run_id, probes) -> EventStream
export_checks(run_id) -> list[CheckerEvidence]
normalize_and_join(run_id, bin_manifest) -> EvidenceBundle
replay(trace_id, model_revision) -> ReplayResult
```

Coverage 数据交换可以采用工具原生导出或经验证的 UCIS 接口。UCIS 提供 coverage API 与交换格式；具体厂商版本支持的格式和粒度仍需要本地小实验确认。[Accellera UCIS 说明](https://accellera.com/news/press-releases/90-accellera-systems-initiative-rolls-out-the-unified-coverage-interoperability-standard-ucis)

原生数据库提供 bin 计数，旁路 JSONL 提供事件 witness；二者必须按 generated bin manifest 对上。未知 bin、缺失映射、重复路径和无法解释的计数差异均阻断 verified-hit。cross 需要具体 tuple 映射，不能只按 covergroup 名字匹配。

用户已有环境是主运行端，当前 Windows 目录是设计与编排工作区；不假设商业仿真器就在本机 PATH。运行端可以按现有流程执行脚本再回收 bundle，无需一开始搭建远程服务。

## 7. 目标实现目录（首版实际布局见06文档）

```text
src/coverage_closure/
  spec/             # 文档与要求清单、来源锚点
  ir/               # schema、AST、type/unit/state检查
  obligations/      # 验证目标与bin清单
  codegen/          # deterministic templates + source map
  adapters/         # 已有DDR5 TB及商业仿真器
  evidence/         # manifest、事件入库、去重、版本失效
  diagnosis/        # 规则、差分、probe选择、可选概率排序
  repair/           # 事务、影响分析、回归门槛
  reporting/        # 双向追踪、未解决项、关闭决策
benchmarks/ddr5_vref/
  scope/ ir/ golden/ traces/ mutants/
configs/ schemas/ tests/ runs/
```

其中 golden 不从被测生成器自动产出，也不向诊断系统暴露故障标签或隐藏测试答案。
